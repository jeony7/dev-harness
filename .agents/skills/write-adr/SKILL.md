# 설계와 단계 논의

메인은 `docs/PDR.md`, 실제 코드·실행 환경, 해당 스택 규칙을 읽고 `docs/ADR.md`를 갱신한다. 작업 에이전트로 배정받았다면 지정한 조사·검토 결과를 메인에게 반환한다.

- API·데이터/상태·화면 흐름·실행 구조·실패 처리를 필요한 만큼 설계하고 관련 REQ/AC를 연결한다.
- 중요한 선택에는 검토한 대안·선택 이유·감수한 단점·검증 방법을 남긴다. 사소한 코드 스타일마다 결정을 문서화하지 않는다.
- 구현을 여러 Step으로 나누는 안을 먼저 제안한다. Step ID, 범위, 선행 조건, 관련 AC, 완료 기준·검증 방법을 기록하고 사용자와 논의한다. 설계 요청만으로 구현하지 않는다.
- 일정·위험·의존성에 맞춰 나누고 단계 수를 고정하지 않는다. 핵심 흐름을 작게 연결하고, 환경·AI 연결이 중요한 불확실성이면 먼저 확인할 단계를 제안한다.
- 독립 조사나 병렬 구현에 실익이 있으면 [에이전트 운영](../../../docs/SUBAGENTS.md)에 따라 코드·대안 조사를 위임하고 메인이 설계를 통합한다. 서버·프론트 병렬 구현을 계획한 Step에는 API·상태 계약, 담당별 수정 범위·검사, 메인의 공통 설정·통합 책임을 기록한다.
- 합의한 내용과 미정 사항을 구분한다. 구현은 사용자가 지정한 Step 또는 명시한 연속 범위에서 진행한다. 이미 합의한 부분을 반복 승인받지 않는다.
