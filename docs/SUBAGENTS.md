# 에이전트 협업 운영

현재 요청 범위에서 작업량·독립성·전달/조율 비용을 보고 직접 수행·일부 위임·여러 담당자 분담을 선택한다. 메인이 서버·프론트 중 한쪽을 맡고 다른 쪽만 위임할 수 있다. 양쪽을 위임할 때는 각각 충분한 독립 작업이 있고 메인이 맡을 통합 작업이 있어야 한다. 구현은 합의한 Step 안에서 수행하며, 작은 작업이나 의존성이 높은 작업은 메인이 직접 처리한다.

위임 전에 결과 수집 방법, 작업 폴더 공유/분리, 동시 실행 가능 여부를 확인한다. 위임할 수 없으면 순차 수행한다.

## 단계별 분담

| 단계 | 위임하기 좋은 작업 | 메인의 책임 |
|---|---|---|
| PDR | 자료별 조건·예외·근거 추출, 확인할 질문 제안 | 사용자와 요구사항·우선순위 확정, PDR 갱신 |
| ADR | 기존 코드 조사, 중요한 대안·연결 위험 검토 | API·상태 계약, Step·의존성·담당 범위 정리와 논의 |
| 구현 | 같은 Step의 서버·프론트 구현과 각 영역 검사 | 공통 설정, 계약 변경 조율, 결과 수집, 통합 검증 |
| 리뷰 | AC 누락 대조, 경계·실패 사례와 코드 검토 | 관찰·실행 근거 대조, REVIEW 최종 판정 |

PDR·ADR 단계의 위임은 조사·제안 범위다. 설계 요청만으로 구현을 시작하거나 위임을 이유로 승인된 Step 범위를 넓히지 않는다. 배정받은 담당자는 전달받은 지침을 따르고 별도 지시 없이 재위임하지 않는다.

## 서버·프론트 병렬 구현의 선행 조건

메인이 `docs/ADR.md`에 해당 Step의 다음 내용을 먼저 정리하고 양쪽에 동일하게 전달한다.

- 메서드·경로, 요청·응답 필드와 타입·필수 여부, 정상·빈 결과 예시
- 오류 상태 코드·응답 형식, 인증·소유권과 필요한 상태 전이
- 실제 파일 기준 서버·프론트 수정 범위와 각 영역의 검사 명령
- 공유 타입·스키마·루트 설정·lockfile·문서의 편집 담당, 통합 완료 기준

기존 계약이 있으면 재사용한다. 계약이 미정이거나 환경이 실행되지 않으면 필요한 조사와 최소 기동 확인을 먼저 수행한다. 기능 전체를 서버·프론트로 길게 분리하기보다 같은 Step의 작은 사용자 흐름을 연결해 확인한다.

서버 담당은 API·업무 로직·저장 처리·서버 테스트, 프론트 담당은 화면·API 클라이언트·로딩/빈 결과/실패 상태·프론트 검사를 맡는다. 실제 폴더명은 프로젝트 구조를 따른다. 계약을 따른 임시 응답으로 화면 개발을 시작할 수 있으며, 최종 검증에서는 실제 서버에 연결하고 임시 응답 사용 범위를 구분한다.

계약 변경이 필요하면 담당자는 이유·영향·제안을 메인에게 보고한다. 메인은 합의된 요구사항 안에서 계약을 조정하고 양쪽에 변경을 전달한다. 요구사항이나 구현 범위까지 바뀌면 기존 사용자 합의 절차를 따른다.

## 작업 전달과 실행

메인은 필요한 맥락을 위임 메시지에 명시한다. 공통 지침·스킬·부모 대화·다른 에이전트의 대화가 자동 공유된다고 가정하지 않는다. 파일을 읽을 수 있는 담당자에게는 관련 섹션·경로를 지정하고, 접근할 수 없으면 필요한 내용을 함께 전달한다.

관련 REQ/AC·Step·API 계약의 섹션과 담당 코드·테스트를 먼저 지정한다. 담당자는 호출 관계·공유 타입·검사 실패 등 추가 근거가 필요할 때 범위를 넓힌다. 메인이 확보한 사실·결정은 근거 위치와 함께 전달하고, 담당자는 맡은 작업에서 필요한 부분을 확인한다. 이미 전달받은 유효한 내용을 얻기 위해 전체 자료를 다시 조사하지 않는다.

```text
역할: 서버 구현 / 프론트 구현 / 자료 조사 / 리뷰 중 이번 작업의 역할
지침: AGENTS.md와 현재 단계의 지침, 재위임·공통 문서 편집 범위
범위: 합의된 STEP ID와 관련 REQ/AC, 포함·제외 항목
참고: 관련 REQ/AC·Step·계약의 섹션, 담당 코드·테스트 경로, 필요한 스택 규칙
수정: 실제로 소유할 파일·디렉터리 또는 읽기만 수행
검증: 실행할 검사와 완료 기준, 공유 자원 사용 담당
보고: 결과 요약, 변경 파일, 실행 명령과 결과, 미확인·차단 사항
```

- 동시에 같은 파일을 수정하지 않도록 담당을 나눈다. 같은 작업 폴더라면 다른 담당자의 미완료 변경을 되돌리거나 덮어쓰지 않는다. 작업 폴더가 분리되어 있으면 변경 전달·반영 방법을 정하고 메인이 실제 반영한 상태에서 통합 검증한다.
- PDR·ADR·REVIEW·RUNBOOK은 메인이 최종 갱신한다. 담당자는 결과를 메인에게 반환하며 별도 보고서가 꼭 필요할 때만 서로 다른 경로에 작성한다.
- 공유 루트 설정·lockfile·코드 생성 산출물의 변경은 메인이 수행하거나 한 담당자에게 명시적으로 맡긴다. 같은 빌드 산출물·DB·포트·브라우저를 쓰는 검사도 실행 담당을 지정한다. 독립된 서버·프론트 검사는 병렬 실행할 수 있다.
- 메인은 위임과 겹치지 않는 통합 준비·독립 작업을 진행한다. 담당자가 작업 중인 파일을 동시에 수정하지 않는다.
- 담당자는 범위 밖 수정이 필요하거나 작업이 막히면 현재 결과와 원인을 보고한다. 메인은 가능한 작업을 이어가며 필요한 선행 조건을 해결한다.

## 결과 수집과 통합

1. 담당자는 변경한 파일, 관련 REQ/AC, 실행한 검사와 실제 결과, 남은 문제를 간결하게 반환한다. 추론·미실행·차단을 통과와 구분한다.
2. 메인은 필요한 담당자의 결과를 모두 수집하고 실제 변경과 검사 근거를 확인한다. 아래 재사용 기준에 맞는 결과는 이어서 사용하고, 변경·실패·불확실성의 영향을 받는 검사만 다시 수행한다.
3. 수정이 필요하면 같은 담당자에게 후속 작업을 요청한다. 사용할 수 없으면 요약·현재 계약·변경 파일을 전달해 새 담당자나 메인이 이어간다.
4. 메인은 실제 화면 → API → 저장/처리 → 화면 반영과 중요한 실패 흐름을 확인한다. 재사용 가능한 통합 실행 근거가 없다면 실제 연결을 검증한다. 각 영역의 lint·테스트·빌드 성공만으로 통합 성공을 판정하지 않는다.
5. 계약 불일치와 통합 오류를 담당 범위별로 수정하고 필요한 검사를 다시 수행한다. 메인이 ADR의 Step 결과, REVIEW의 AC 판정, RUNBOOK의 실행 안내를 갱신한다. 합의된 완료 기준을 충족하지 못하면 미완료·차단·미검증을 그대로 보고한다.

리뷰 결과는 구현 주장과 독립적인 근거로 대조한다. 가능하면 구현 담당자와 다른 에이전트에게 검토를 맡기고, 변경 중인 구현을 본 중간 결과는 최종 결과와 구분한다. 사용이 끝난 담당자는 필요한 결과를 수집한 뒤 도구가 지원하면 닫는다. 중요한 결정과 복구에 필요한 내용은 프로젝트 문서에 남긴다.

## 검사 결과 재사용

- 코드·설정·의존성·입력 데이터·실행 환경이 같고 검사 명령·범위·결과를 확인할 수 있으면 기존 근거를 재사용한다. 담당자나 단계가 바뀌었다는 이유만으로 같은 검사를 반복하지 않는다.
- 상태 변경·수정·검사 실패·재현 불일치나 근거 부족이 있으면 영향 있는 검사를 실행한다. 기존 결과의 범위가 현재 AC를 포함하는지 확인하고, AC가 바뀌면 기존 판정을 재검토한다.
- 서버·프론트의 부분 검사와 실제 연결 검증은 구분한다. 미확인 통합 흐름은 실행하고, REVIEW에는 실행한 검사와 재사용한 기존 근거를 구분해 남긴다.

위임이 실패하면 가능한 범위를 메인이 이어서 수행하고, 수행하지 못한 작업과 사유를 보고한다.
